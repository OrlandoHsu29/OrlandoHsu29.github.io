Wrist-Talk 智能腕表系统

STM32F411CEU6（Cortex-M4F @100MHz，512KB Flash / 128KB RAM）+ FreeRTOS（CMSIS-RTOS2）+ LVGL 的智能手表固件工程。 我把「企业级固件架构」落地到一颗 MCU：五层单向依赖架构、Active Object 业务无共享锁并发、OOP-in-C 驱动体系、 七级自动初始化、声明式低功耗引擎、IAP BootLoader（App 位于 0x0800C000）。

$ 项目概述 overview/

这个项目源自 Cane 适老化 AI 终端的产品构想：语音主交互 + 按键辅助。但那套 ESP32 + OpenClaw 的技术栈 与企业嵌入式开发的主流技术栈契合度不高，于是我把它 重构为一套基于 STM32 技术栈的智能腕表系统——硬件无法完全满足 产品设计，但整套技术栈（STM32 / FreeRTOS / LVGL / IAP）是嵌入式产品中常见的组合，值得系统掌握。

工程定位为面向企业固件实践的学习工程：架构上采用分层与依赖注入，并发上采用 Active Object 模型（各对象串行处理自己的状态，业务层不共享可变状态）， 驱动上采用 OOP 与表驱动，可靠性上引入看门狗、统一错误码与三层防线校时，并以单槽双保险 IAP BootLoader 收尾， 设计借鉴 Linux 内核与 AUTOSAR 的工程思想。

$ 工作内容 core/

本项目核心开发工作包含 5 个部分：五层架构 · 并发框架 · 面向对象驱动 · 低功耗 · OTA。

1.五层架构 2.并发框架 3.面向对象驱动 4.低功耗 5.OTA

1. 五层单向依赖架构

借鉴 AUTOSAR 分层思想 + Linux 设备模型，把固件拆成五层，上层只依赖下层，下层绝不 include 上层；跨层事件通知一律用回调注入（DIP）。

arch.svg · 五层单向依赖
  • Board 硬件描述：所有引脚 / 地址 / 参数（LED active_low、按键消抖时间、LCD 分辨率、3 条 I2C 总线的 SCL/SDA、传感器地址、看门狗引脚）集中在一个编译期静态文件里，轻量版 Device Tree。
  • 组合根（App/device_registry.c）：全系统唯一「创建对象 + 依赖注入」点。分三级挂载：DEVICE 级创建总线句柄 → COMPONENT 级创建全部芯片驱动 + 回调注入 + probe（ops->init 校验 ID，失败 Error_Handler 停启）→ READY 级开启外部看门狗。
  • 依赖铁律：上层只依赖下层，下层绝不 include 上层；MCU 相关实现集中在 Core / Platform / Board，迁移 MCU 时主要替换这些适配层。

2. Active Object 并发框架

参考 QP/C 与 Linux workqueue 思想：每个 Active Object = 一个 FreeRTOS 任务 + 私有消息队列（深度 16）+ dispatch 分发函数。事件载荷 12 字节内联传值，ao_post_event 可在 ISR 中安全调用——跨上下文无指针生命周期问题。

ao_base.c · ISR → 队列 → 任务
  • 两段式管线：ISR 只做限流与投递（如按键 EXTI 里 tick 消抖 + 只投 key_id），业务判断全在任务上下文。
  • LVGL 线程边界：LVGL 非线程安全，跨线程 UI 更新统一投递到 LvglTask 上下文执行；HomeAO 的 dispatch 只更新业务数据，再通过 lv_async_call 异步触发 UI 操作。
  • RTOS 抽象（Platform/os_if.c）：队列 / 互斥 / 事件标志 / 任务 / 延时集中封装成项目自有接口，迁移 RTOS 时将适配范围收口在这一层。
  • 统一错误码：error_t enum（非 #define，调试器可见符号名）；「count-or-error」模式对齐 Linux 内核（正数=字节数、负数=错误码）。

3. OOP-in-C 驱动体系

七级自动初始化 仿 Linux module_init / RT-Thread INIT_EXPORT

7 级：BOARD→PREV→DEVICE→COMPONENT→ENV→APP→READY，每级执行完才进下一级，同级按 order 排序。新增模块只新建 .c + 一行宏，零侵入旧代码（开闭原则）。

/* 宏把初始化条目放进链接器段（ARMCC），.sct 收集，运行时按级遍历 */
#define INIT_APP_EXPORT(fn)                                       __attribute__((section("InitEntries")))                         const init_entry_t _init_##fn = { fn, ORDER_APP }

调用点在 freertos.c 的 CubeMX USER CODE 保留区（osKernelInitialize 之后、osKernelStart 之前，串行执行）——CubeMX 重生成不丢。运行时用 ARMCC 边界符号 Image$$ER_INIT_TABLE$$Base/Limit 遍历执行。

SPI + ST7789 显示屏 软件 NSS + DMA 渲染管线

  • CS 软件控制：传输前拉低，DMA 完成后确认 SPI 已发送完毕（检查 TXE / BSY）再拉高，保证 ST7789 一次命令或整帧传输期间 CS 持续有效。
  • 初始化序列表驱动：st7789_init.h 是厂商寄存器纯数据表，lcd_send_init_sequence 是通用发送器——换 ILI9341 只换表。
  • 最终像素数据走 SPI DMA：窗口命令用阻塞 SPI 完成后，lcd_write → spi_transmit_dma → HAL_SPI_TxCpltCallback → 等待 BSY=0 → lcd_notify_flush_done → lv_disp_flush_ready；DMA 完成前不占用 CPU，CS 在整个窗口命令 + 像素数据事务期间保持低电平。

UART：DMA 接收 + 手动 IDLE 中断帧检测 + 环形缓冲

  • HAL_UART_Receive_DMA 配合手动开启 IDLE 中断：ISR 读取 DMA 剩余计数得到本帧长度，记录到 volatile 变量，并调用 ISR-safe 的事件标志接口唤醒消费任务；帧解析仍由任务完成。
  • 任务侧 uart_read_frame 消费：更新环形缓冲写指针（256B、2 的幂掩码取模）→ 置事件标志 → 阻塞等帧 → 读出。
  • 承载两路业务：调试 AT 控制台 + BLE 模块（KT6328）透传通道。

软件 I2C 位带 DWT 微秒延时

  • SCL/SDA 用 GPIO 翻转实现完整时序：START/STOP/ACK 检测/8 位收发/Repeated START（寄存器访问「写地址后不 STOP 直接再 START 切读」）。
  • 微秒延时用 DWT 周期计数器而非 NOP 循环（NOP 依赖优化级别会漂移）或 SysTick（归 FreeRTOS 所有）——bug 复盘修出的正确实现。
  • ACK 无应答返回 ERR_DRV_I2C_ACK；3 条独立总线（传感器 / EEPROM / 触摸）。

BLE 通讯：KT6328 透传 + AT 命令引擎

  • 手机 App ↔ BLE ↔ UART 帧 ↔ MCU，AT 协议承载业务命令；at_parser 注册制命令引擎，命令表由 App 层注入（组合根），引擎只做路由。
  • OV 家族命令：OV+VERSION（版本号单一信息源 version.h）、OV+SEND（上报温湿度时间等 7 行数据，读取单写者缓存）、OV+ST= 校时——三层防线：逐位数字校验 → 范围校验 → 驱动返回值校验，外部输入永远不可信。
  • 手写扫描切分命令名（不用 strtok/sscanf——不可重入 / 格式僵化）；未知命令显式报错，不静默吞掉。

传感器统一采样调度 TIM 硬件节拍

TIM11 50ms 溢出中断 → ao_post_event 投递节拍（ISR 只投事件）→ SensorAO dispatch 串行执行：高频通道每 50ms 采 PPG 原始波形（20Hz 满足当前心率估计需求），低频通道按分频（先加后除防截断）采温湿度 / 姿态 / 罗盘 / 气压。结果写入 g_sensor_cache，由单一写者更新，BLE 命令任务只读。

4. 低功耗设计

按电源域从浅到深拆解三种低功耗模式，回答「谁还在供电 / 唤醒源 / 唤醒代价」三个问题：

模式电源域唤醒源唤醒代价
SLEEPCPU 停止取指，已开启时钟的外设继续运行，SRAM/寄存器保持任意中断无需重配时钟，按中断延迟恢复执行
STOP大部分外设时钟停止、SRAM 保持、RTC/备份域活EXTI / RTC 唤醒定时器需重配系统时钟，延迟取决于时钟配置
STANDBY仅备份域（RTC+备份寄存器），SRAM 清零RTC / WKUP 引脚冷启动（进 Reset_Handler）

六种声明式功耗场景（power_model_t 纯数据表）：背光百分比、传感器采样周期（0=全部 sleep）、BLE 模块电源开关、事件处理完后的入睡深度。

场景背光采样周期BLE入睡深度
ACTIVE80%50ms开RUN
DIM10%500ms开—
IDLE关屏传感器全睡关SLEEP
STOP息屏—关STOP（仅 RTC 活）
CHARGE常亮正常开不省电
SPORT常亮全速开—

超时迁移也是声明式表：ACTIVE 无操作 10s→DIM，30s→IDLE，60s→STOP；CHARGE/SPORT 无超时降级。

面向切面（AOP）的功耗引擎（App/power_manager_ao，借鉴 Linux cpuidle / RT-Thread pm 的模式管理思想）：业务模块只发布事件（按键/触摸/充电/抬腕），不直接编写省电操作；引擎按迁移规则表逐子系统 diff 执行过渡——LCD 0↔非0 走 open/close（面板 Sleep Out/In + PWM），非 0 之间走 ioctl 亮度；传感器采样周期经 SensorAO 命令队列修改，以队列作为串行化边界；BLE 模块直接断电（KT6328 电源脚 PA8）。

关键细节：STOP 前清 WU/SB 唤醒标志 + HAL_SuspendTick()（防 pending tick 唤醒、防唤醒后时钟未重配时 tick 错频）；入睡循环「排空队列遗留事件 → 入睡 → 唤醒 → 再排空」；外部看门狗用 OS_PRIO_LOW 最低优先级喂狗——业务全卡死时喂狗排不上队，狗超时复位（看门狗本意）。

5. OTA：单槽双保险 IAP

BootLoader 与 App 采用明确的 Flash 分区：BootLoader 占用 S0–S1，S2 保存升级标志，App 从 0x0800C000 启动。受 512KB Flash 容量限制，App 区约 464KB，无法同时容纳两份完整镜像，因此采用「单槽 + 双保险」方案，保证掉电后不跳转到半成品。

flash.svg · 分区（单一信息源 shared/ota_protocol.h）

双保险掉电安全

  1. 保险一（先作废再写入）：升级第一步擦 S2 清 FLAG 作废旧固件——升级中途掉电，上电后 BootLoader 看到无有效标记，停在升级模式等重传，绝不跳半成品。不变量：「FLAG 存在 ⟺ 固件完整」，靠时序维持。
  2. 保险二（整包校验）：Ymodem 收完固件后对 Flash 完整镜像算软件 CRC-32（查表法 20 行，自检向量 "123456789"→0xCBF43926），与 footer 8 字节（[CRC32 LE][长度 LE]，pack_ota.py 打包脚本追加，与 Python zlib.crc32 同参数）比对，通过才写回 FLAG。
  3. 跳转前向量表合法性校验：读 App 向量表头两个 word——SP 必须在 RAM 区间、PC 必须在 App 区，不信任「看起来像有效」的 FLAG。
/* 跳转前校验：不信任"看起来有效"的标记 */
uint32_t sp = *(volatile uint32_t *)APP_BASE;
uint32_t pc = *(volatile uint32_t *)(APP_BASE + 4);
if (sp < RAM_BASE || sp > RAM_END) return ERR_BAD_SP;
if (pc < APP_BASE || pc > APP_BASE + APP_MAX) return ERR_BAD_PC;

BootLoader → App 六步跳转（寄存器级）

① __disable_irq() 关全局中断 → ② HAL_RCC_DeInit()+HAL_DeInit() 复位外设到上电默认 → ③ SysTick 三个寄存器清零 → ④ SCB->VTOR = 0x0800C000 重定位向量表 → ⑤ 读 App 向量表 [0]=MSP、[4]=Reset_Handler → ⑥ __set_MSP() + 跳转。顺序不能乱（先 VTOR 再跳，否则第一条指令前中断进错表）。

升级触发（两条路径）与 Ymodem

  • 升级触发：按住 KEY1 上电（500ms 防抖二次确认），或由 BLE 命令写入 RTC 备份寄存器魔数（0x4F54414F）后执行 NVIC_SystemReset()；BootLoader 检测到魔数后进入升级模式并清除魔数。选备份寄存器而非 Flash 标志：写 Flash 要擦扇区、阻塞取指并影响看门狗协作；备份寄存器是纯寄存器写，速度快，且只要备份域仍由 VBAT 供电就能跨软件复位保留。
  • Ymodem：STX 1024B 大帧 / SOH 128B 小帧，帧头（序号+~序号）+ CRC16；接收状态机「发 'C' 进 CRC 模式 → 收文件名包（解析声明大小，超限拒绝）→ 擦 App 区 → 逐帧收数据写 Flash（每帧 CRC16 + 序号校验，错误 NAK 重传，10 次超限取消）」；修复原版 ST 例程的坑：末帧不足 1024B 按声明大小截断、不把 0x1A 填充写进 Flash；尾部不足 4 字节补 0xFF 凑整字。
  • 看门狗协作：进升级模式启用外部看门狗，Ymodem 等待 / 接收循环正常喂狗；Flash 擦除期间取指可能暂停，因此看门狗超时时间覆盖单次擦除窗口，并在每次擦除之间喂狗；跳转前关闭看门狗——升级挂死时自动复位并重进升级模式。
  • 工具链：BootLoader 与 App 各一份手写 .sct，App 链接地址为 0x0800C000 并保留七级初始化的 ER_INIT_TABLE 段；After Build 自动调用 pack_ota.py 生成带 CRC-32 footer 的升级包。
